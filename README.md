# CONNEZER EDUTECH SYSTEMS

CONNEZER EDUTECH SYSTEMS is an Education Technology (EdTech) brand serving private schools in Ghana with configurable school-defined levels from early years through secondary and vocational programmes. Its subtitle is SMART SCHOOL MANAGEMENT SYSTEM and its tagline is Smart Technology. Better Education. The platform uses a navy-blue and white foundation with light blue, restrained green, teal, and gold accents. This PHP 8.1+ / MySQL application uses server-rendered HTML, CSS, and vanilla JavaScript and retains its existing authentication, mandatory email OTP, optional additional authenticator verification, password recovery, account profiles, and activity records.

The portal uses the supplied CONNEZER education-and-technology brand image on public and platform pages. Each school workspace sidebar continues to use only that school's verified name and logo. Public app assets are under `public/assets/images/`.

The shared application UI uses a navy-blue and white foundation with restrained green, teal, sky-blue, purple, and amber accents. Shared layouts and `public/assets/css/app.css` provide the consistent navigation, responsive cards, tables, forms, and print styles across public and authenticated pages; `public/assets/js/app.js` provides shared, permission-neutral interactions. Role-specific data and authorization continue to be enforced by each page.

The existing application also retains its association features, including member applications and role assignments, an active-member directory, events and attendance, announcements, dues and payments, meetings, private documents and messaging, and reports. School accounts use the separate school-membership model and school-specific authorization described below.

Member messages are persisted in MySQL and retained indefinitely; opening or reading a conversation only updates read timestamps and never removes message rows. Apply migration 030 before deploying the delivery-receipt update. A sent message has one grey tick, delivery to the recipient's authenticated messaging page records `delivered_at` and shows two grey ticks, and an incoming message receives `read_at` only after it is at least 60% visible in the open conversation, showing two blue ticks to its sender.

Mentorship discovery and consent-based connections use the existing mentorship profiles and in-app notification system. Apply migration 031 before deploying the mentorship connection page. Members can opt in as mentors, seekers, both, or opt out; only visible profiles appear in search. Requests remain pending until the intended recipient accepts, and ending a mentorship connection does not remove the separate private-message conversation or history.

## 1. Architecture and local setup

The browser talks to PHP pages in `public/`. Shared authentication, database, mail, and security logic is under `app/`; secrets and database connection settings are in `config/local.php`, outside the public web root. MySQL stores users, roles, one-time token hashes, rate-limit events, and security logs. PHPMailer sends real messages over configured SMTP. Authorization is checked on every protected PHP request—not just by hiding navigation links.
Member chat uses authenticated same-origin AJAX polling every five seconds and does not require WebSocket support. Apply database migrations 028–031 before deploying the member-submission, messaging, receipt, and mentorship updates.
The school portal's migrations 032–060 are in `database/migrations/` and should be applied in numeric order before deploying the corresponding school-tenant and student-portal changes. Migration 035 adds an optional per-user profile photo path; school logos use the existing `schools.logo_path` field. Migration 036 standardizes recognized legacy class-level aliases, flags unrecognized levels for review, and supports the fixed class-level choices used by the school class manager. Existing class IDs and related student and academic records are retained. Migration 037 adds school/class/year/period fee schedules, effective-dated fee history, invoice snapshots, payment verification, and approved invoice adjustments without rewriting issued invoices. Migration 038 creates explicit, school-scoped class-teacher assignments for each academic year and migrates the existing class-teacher links. Migration 039 adds non-destructive student exit/reinstatement history, private supporting documents, and consented two-school record-transfer approvals without deleting or rewriting student, academic, or financial history. Migration 040 adds verified student-account links, result publication timestamps, class timetables, and student assignments/material links. Migration 041 stores the applicant's date-of-birth claim only while a student-link request is pending; approval clears it. Migration 042 changes password recovery to one-time six-digit email codes. Migration 043 introduces school-scoped role requests, per-role approval/rejection records, approval evidence notes, revocation events, and supports multiple independently approved school roles while retaining only one selected role's permissions at a time. Each school has at most one active Proprietor. Replacing that owner requires the current sole Proprietor to approve a pending Proprietor request with explicit transfer confirmation, eligibility-evidence confirmation, and a recorded reason; the transfer is audited and both parties are emailed. For the attendance/results workflow, apply migrations 047–052 in order after 046; migration 047 establishes the class/date attendance submission table required by later attendance migrations, and migration 052 adds school grading/ranking settings, revision history, report-card snapshots, and school-scoped notifications. Migration 055 creates school-scoped academic-year and admission-sequence records, retains terms and class references, and adds admission dates and an optional admission abbreviation without changing existing student numbers. Migration 056 adds a default-private explicit public flag for calendar events; `public/public_school_calendar.php` only serves events marked public and published. Migration 057 adds the school administrative-designation history table. Migration 058 adds additive verified parent links and audit history while preserving legacy guardian fields and records.

The service worker caches static assets and a data-free offline notice only. It never caches authenticated school pages or student/staff records. Student attendance drafts can be retried while the authenticated register remains open, but are held only in page memory and are lost if the page reloads or closes. Results and other school workflows do not synchronize offline.

The Teaching and Learning workspace lets authorized school leaders and assigned class/subject teachers publish school-scoped homework and assignments. Active, linked student accounts can view published instructions, optional Ghana-local due dates, and HTTP(S) learning-material links for their current class. Assignment submissions, grading, attachments, and late-work rules are not enabled.

- **Database connection error:** start MySQL in XAMPP, import the schema, and match host/port/name/user/password in `config\local.php`. Set `db.port` to the port MySQL is listening on (3306 by default). Confirm PHP's `pdo_mysql` extension is enabled.
- **Email says delivery failed:** the app did not claim success. Install Composer dependencies; configure SMTP host, port, username, password/app password, encryption, and sender address. Check outbound SMTP access, PHP `openssl`, and Apache/PHP logs. Use Resend after its cooldown.
- **Email OTP is delayed or expired:** request a new code after the one-minute cooldown and use the newest message within five minutes. Older codes are invalidated.
- **Authenticator code is rejected:** check the phone's automatic date/time; codes change every 30 seconds. Confirm the app entry is time-based, six digits, SHA-1. If necessary, use an unused recovery code.
- **`SODIUM_CRYPTO_SECRETBOX` undefined:** enable PHP's `sodium` extension in XAMPP's `php.ini`, restart Apache, and check `php -m`.
- **A protected page returns 403:** that is expected if the current account lacks that role. Assign roles only through the administrator interface or a trusted local database session.

## 2. Database relationships

`users` has a many-to-many relationship with `roles` through `user_roles`. The remaining user-owned tables use `user_id` foreign keys and cascade when a user is deleted: email verification and login OTP state, encrypted TOTP seed, hashed one-time recovery codes, hashed password-reset tokens, and legacy remember-me validators. The legacy `email_otp_enabled` and `remember_tokens` schema fields remain for compatibility, but sign-in ignores the toggle and never restores or issues remembered sessions. `login_attempts` stores keyed hashes of identifiers and IP addresses for rate limiting. `security_logs` records event names and safe metadata only; secrets and passwords are never logged.

Public registrations receive the `ordinary_member` role. Assign technical and association roles through the protected role-administration workflow; never expose role assignment to public registration.

## 3. User journey and security behavior

- Registration validates the data on the server, stores a `password_hash()` result (Argon2id when supported, otherwise PHP's default algorithm), assigns `ordinary_member`, and emails a six-digit code. Verification codes expire in five minutes, have five attempts, are stored as keyed hashes, and can be resent no more than once per minute.
- Login accepts username or email. A successful password is not enough for an unverified or disabled account: every sign-in requires an emailed OTP, even when the legacy per-account setting is off. An enabled authenticator TOTP is an additional factor and cannot replace email OTP. TOTP uses standard 30-second RFC 6238 codes and can be entered in Google Authenticator or Microsoft Authenticator after adding the displayed secret.
- If an account has an invalid legacy email address, sign-in is blocked. A Platform Super Admin can use `public/platform_email_correction.php` after confirming the account holder's identity through an approved out-of-band process and re-entering the administrator password. The new address is marked unverified, pending codes are invalidated, and the account holder must complete email verification before signing in.
- Recovery codes are random and stored only as password hashes. They are single-use. Save the displayed codes safely; they cannot be retrieved later.
- Remembered-session authentication is disabled. Legacy remember-token rows are not used to authenticate; an old remember cookie is expired when an unauthenticated request reaches the application. Logout revokes a matching legacy token if its cookie is still present, destroys the authenticated session, and authenticated pages are sent with no-store cache headers.
- Password recovery emails a six-digit code stored as a keyed hash. Codes expire after five minutes, allow five attempts, and can be requested no more than once per minute (three times per account per 15 minutes). Successful resets revoke persistent-login tokens.
- CSRF tokens protect all state-changing forms; output is escaped; prepared statements are used throughout; session IDs rotate after authentication; cookies are HttpOnly, SameSite=Strict and Secure on HTTPS.
- After all login factors pass, one-role accounts continue to that role's dashboard. Multi-role accounts choose only from roles assigned in `user_roles`; every switch is checked against the database, and server-side permissions use only the selected role.

The pepper is a server-side secret used as an additional keyed input to password hashing; it is not a replacement for the unique salt PHP generates as part of `password_hash()`. Changing the pepper invalidates existing password hashes, so maintain a protected backup and rotation plan.

### Safely remove a disposable unverified test account

Back up the database outside the web root first. From PowerShell, create a SQL dump:

```powershell
$backup = 'C:\Users\Ebenezer\Desktop\secure_auth_system-before-test-cleanup.sql'
& 'C:\Users\Ebenezer\Desktop\2FA\mysql\bin\mysqldump.exe' -u root "--result-file=$backup" secure_auth_system
if ((Get-Item -LiteralPath $backup).Length -eq 0) { throw 'Database backup is empty; do not delete any accounts.' }
```

Confirm the dump exists and is non-empty. In phpMyAdmin, first inspect the exact test email with a `SELECT` and ensure it is the disposable unverified account. Then run this transaction, replacing the example with that exact email:

```sql
START TRANSACTION;
DELETE u
FROM users AS u
WHERE u.email = 'exact-disposable-test-address@example.com'
  AND u.email_verified_at IS NULL
  AND NOT EXISTS (
    SELECT 1
    FROM user_roles AS ur
    JOIN roles AS r ON r.id = ur.role_id
    WHERE ur.user_id = u.id
      AND r.name = 'administrator'
  );
SELECT ROW_COUNT() AS deleted_accounts;
```

Commit only if `deleted_accounts` is exactly `1`; otherwise `ROLLBACK`. This exact-email condition and verification/administrator safeguards prevent a broad cleanup or deletion of an administrator. Do not target a verified or real member account. Foreign keys remove only the selected account's dependent authentication records; security-log entries remain with their user reference set to null.

Headmasters and Proprietors with attendance-management permission use **Staff attendance & punctuality** to set schedules by staff category, monitor the daily register, record or correct records with a reason, review disputes, and manage make-up attendance. Staff attendance report pages and exports are not provided; daily attendance records remain saved and are still used by payroll. Configure the school timezone, reporting/departure rules, and working days. During initial school setup, authorize at least one school-managed attendance device (computer, tablet, or laptop) before using the kiosk; the setup checklist remains incomplete and the kiosk rejects unregistered devices until one is active. Administrators may authorize additional devices later. Register each device from its browser during an authorized administrator session; it receives an HttpOnly, SameSite=Strict credential, while the database stores only its keyed hash. Deactivate a device if the computer or browser profile is replaced. Device registration is a bearer-token control, not hardware attestation: administrators must protect the operating-system account and browser profile, use HTTPS in production, and deactivate a device if it may have been copied or compromised. The kiosk route has no application navigation and accepts attendance transactions only from an active device after setup. It does not lock the computer into kiosk mode; the authorized administrator can still use the normal portal.

The kiosk accepts a Staff ID and attendance PIN only; portal email/password are separate. Transactions use school server time and timezone. Staff explicitly choose check-in or check-out. Check-in is accepted from 5:30 AM until before 2:00 PM on a configured working day; check-out is available at any time on a configured working day, but requires an existing arrival and a later server timestamp. Duplicate arrival or departure attempts remain rejected. The schedule's optional clock-out calculation setting controls working-duration and early-departure metrics, not whether a departure can be recorded. A teacher cannot select or submit an attendance timestamp. Existing database uniqueness and transaction checks preserve the first attendance for a school, staff member, and day; rejected attempts are recorded in the administrator's security-event view. Staff receive a specific duplicate message that preserves their original arrival/departure time. The teacher PIN page provides personal history and credential management but does not link to the kiosk.

If a teacher forgets their attendance PIN, they can select **Forgot PIN?** at the kiosk. This does not disclose whether a Staff ID exists. An authorized administrator must verify the teacher in person, initiate the reset, and give them the one-time setup code directly. The old PIN is invalidated immediately; the code expires after 15 minutes and is limited to five attempts. The teacher enters the code at the kiosk and chooses their own new 6–10 digit PIN. Never ask an administrator to view or choose a teacher's PIN. Reset initiations and outcomes appear in the PIN reset audit history; the one-time code is shown only once to the administrator and is stored as a keyed hash.

The attendance dashboard also offers **Record verified arrival now** for a staff member who is physically present but cannot use the kiosk. The authorized administrator must confirm physical presence and enter a reason. The server supplies the current timestamp, labels the event `administrator_recorded`, and refuses to create another daily attendance row. This does not bypass the normal duplicate check-in restriction.

Staff set their own attendance PIN in **Attendance PIN & history**. Kiosk verification applies the school's grace and late thresholds. Membership verification uses an existence check so staff with multiple school roles are not accidentally duplicated during credential lookup. After each attempt, the kiosk uses post/redirect/get so refreshing the browser cannot accidentally submit the same transaction again. A successful confirmation shows the Staff ID, date, time and status, then automatically returns to a clean screen after seven seconds; staff can continue sooner using the on-screen button. The empty kiosk form also resets after two minutes without interaction. Corrections retain the original values and verification method in the audit history; a corrected current record is labelled `administrator_recorded`.

The attendance kiosk does not request or capture photographs. Legacy photo records and files from earlier use are no longer shown; continue scheduling `php database/expire-staff-attendance-photos.php` daily from the application root (for example, with Windows Task Scheduler or cron) until existing files and metadata have expired. Report exports are CSV files that Excel can open; PDF output uses the browser's Print / Save as PDF function. Fingerprint verification requires compatible external hardware and software and is not provided by a standard browser.
